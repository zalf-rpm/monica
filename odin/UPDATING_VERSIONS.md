# Updating the pinned third-party versions

The Odin port has three external dependencies: the **Odin compiler**,
**Cap'n Proto** (for the C++ shim in `support/capnp/shim_dynamic`) and
**zeromq**. There are four ways to build it, and each one gets these
dependencies from a different place:

| | Odin compiler | Cap'n Proto | zeromq |
|---|---|---|---|
| **pixi, Linux** | release tarball, via `tools/odinw.py bootstrap` | vcpkg (manifest mode, generated by `odinw.py capnp-shim`) | conda-forge |
| **pixi, Windows** | release zip, via `odinw.py bootstrap` | vcpkg, `x64-windows-static` | **committed** `support/zeromq/windows/libzmq.lib` (+ conda-forge DLL at runtime) |
| **Nix** (`nix build`) | the same release tarball, `fetchurl` | `pkgs.capnproto` re-pinned to our version | `pkgs.zeromq` from the locked nixpkgs |
| **Docker** (`odin/Dockerfile`, Debian) | `odinw.py bootstrap` | built from the git tag in the image | Debian's `libzmq3-dev` |

All pins live in **`versions.json`**, which `odinw.py`, `../flake.nix` and the
`Dockerfile` all read. `pixi.toml`, `pixi.lock`, `flake.lock` and the committed
`libzmq.lib` cannot read it, so they have to be kept in agreement by hand.
`odinw.py check-pins` checks that they do.

## The workflow for any bump

1. Edit `versions.json` (and whatever else the sections below list).
2. Run the local checks:
   ```sh
   pixi run python tools/odinw.py check-pins
   ```
   This checks that each pin exists for every build path, including Windows. It
   only checks *availability*, not whether things compile. It needs
   `$VCPKG_ROOT` (a vcpkg checkout with full history) and `nix` on `PATH` for
   the vcpkg and Nix checks; without them those checks are reported as `SKIP`.
3. Build and test locally:
   ```sh
   pixi run capnp-shim && pixi run build && pixi run test
   nix build .#monica-odin                          # from the repo root
   docker build -f odin/Dockerfile -t monica-odin . # from the repo root
   ```
4. Push the change as a branch or PR. `.github/workflows/odin.yml` builds and
   tests the pixi path on **Linux and Windows**, plus Nix and Docker. The
   Windows job is the only place the Windows side is actually compiled and
   linked, so wait for it to pass.
5. If numerics could be affected (new Odin compiler, new libm, `-o:speed`), run
   `diff_vs_cpp.sh` against the C++ MONICA. The port's acceptance criterion is
   byte-identical CSV (`CONVENTIONS.md` §1).

## Odin compiler

Edit `odin.tag` and **both** `odin.sha256` entries in `versions.json`:

```sh
TAG=dev-2026-10
curl -sL https://github.com/odin-lang/Odin/releases/download/$TAG/odin-linux-amd64-$TAG.tar.gz | sha256sum
curl -sL https://github.com/odin-lang/Odin/releases/download/$TAG/odin-windows-amd64-$TAG.zip   | sha256sum
```

Nothing else needs editing: pixi, Nix and Docker all take the tag and hashes
from `versions.json`. `pixi run build` notices the new tag and bootstraps it.

Watch out for:
- Odin nightlies can break code or change `core:` behaviour. Run the full test
  suite and `diff_vs_cpp.sh`.
- `ols` in the Nix dev shell comes from nixpkgs, not from this pin, so it may lag
  behind the compiler. That only affects the editor.
- The Linux release binary has to stay statically linked. The Nix package and
  the Docker image both rely on that. If a future release becomes dynamically
  linked, the Nix package needs `autoPatchelfHook`.

## Cap'n Proto

In `versions.json`:

1. `capnproto.version`, e.g. `1.4.0`.
2. `capnproto.nix_src_hash`:
   ```sh
   nix flake prefetch github:capnproto/capnproto/v1.4.0   # prints "hash"
   ```
3. `vcpkg_baseline`, **if** the current baseline doesn't contain that version.
   vcpkg resolves the version through its versions database, so pick a vcpkg
   commit or release tag that already has the version:
   ```sh
   git -C $VCPKG_ROOT fetch --tags
   git -C $VCPKG_ROOT show <tag>:versions/c-/capnproto.json | grep '"version"'
   git -C $VCPKG_ROOT rev-parse '<tag>^{commit}'           # -> vcpkg_baseline
   ```
   A newer baseline also updates the transitive ports (zlib). It does **not**
   need to match `../vcpkg_tag.txt`, which only the C++ build uses.

Watch out for:
- **Your local vcpkg checkout** must be at least as new as the baseline. In
  manifest mode the override is resolved against the checkout's own versions
  database. `check-pins` reports this as `capnproto vcpkg version`.
- **Nix:** `flake.nix` takes nixpkgs' `capnproto` recipe and swaps in our
  source. For a version far from what nixpkgs ships, the recipe may need
  adjustments (patches, CMake flags); `nix build` will show it. When our version
  equals nixpkgs', the override is just a re-pin.
- **Shim code:** the shim's C++ (`support/capnp/shim_dynamic`) may need changes
  for API deprecations or removals. That's a separate repository
  (`mas_capnp_odin_shim`): commit and push there, then bump the submodule here.
- **Windows static variant:** `pixi run capnp-shim-static` merges the shim with
  the Cap'n Proto/kj static libs into one `.lib`. The list of libs is in the
  shim's `CMakeLists.txt`; a new Cap'n Proto that splits or renames libraries
  needs that list updated.

## zeromq

zeromq is the awkward one, because each path gets it from somewhere else:

1. `versions.json`: `zeromq`.
2. `pixi.toml`: the `zeromq = "4.3.x.*"` spec, then `pixi update zeromq`.
   pixi locks `linux-64` and `win-64` together, so if the lock resolves on Linux,
   the conda-forge package exists for Windows too.
3. **Windows import library:** Windows doesn't link conda's zeromq. It links the
   committed `support/zeromq/windows/libzmq.lib`, an import library naming
   `libzmq-mt-4_3_5.dll`. Replace it with the one from the new conda-forge
   `win-64` zeromq package. Its URL is in `pixi.lock`. The `.conda` file is a
   zip containing `pkg-*.tar.zst`, and the file you want is
   `Library/lib/libzmq.lib` in there:
   ```sh
   unzip zeromq-*.conda && zstd -dc pkg-*.tar.zst | tar -x Library/lib/libzmq.lib
   ```
   Then fix the DLL name in the comment at the top of
   `support/zeromq/bindings.odin`. `check-pins` checks the DLL name inside the
   `.lib`.
4. **Nix:** `flake.nix` uses nixpkgs' zeromq and asserts that its version equals
   the pin. If they differ, either run `nix flake update` (this moves *all* of
   nixpkgs, including the compilers) or add a `zeromq.overrideAttrs` like the
   Cap'n Proto one.
5. **Docker:** Debian's `libzmq3-dev`/`libzmq5`. Check its version for the
   `DEBIAN_VERSION` in the `Dockerfile`
   (`docker run --rm debian:13-slim sh -c 'apt-get update -qq && apt-cache policy libzmq5'`).
   Debian only offers one version per release, so a different zeromq usually
   means a different Debian release, or building zeromq from source in the
   image like Cap'n Proto.
6. `support/zeromq/bindings.odin`: the `VERSION_*` constants and the bindings
   themselves, if the C API changed. The constants are compile-time only;
   `check-pins` warns about a mismatch but doesn't fail.

## The C++ reference (`cpp_reference`)

CI (`.github/workflows/odin.yml`) runs the C++ MONICA's test suites -
Hohenfinow2 and the 48 muencheberg_v140 simulations, from `tests/` in the C++
repository - with the Odin `monica-run` on Linux and Windows, and compares the
results value by value against the C++ build at `cpp_reference.commit`. That
commit also pins the suites (`tests/suites.toml`) and `monica-parameters`, so
the comparison only changes when the pin moves. The C++ results are cached per
commit.

To move it, e.g. after a model change in the C++ `master`:

1. Set `cpp_reference.commit` to the full hash of the new C++ commit.
2. Push: the `compare` job shows what differs (job summary). Expected
   differences mean the change still has to be ported to Odin - port it, then
   CI is green again.

`cpp_reference.ignore` lists simulations of features the port doesn't have
(`hohenfinow2/sim-min-ic`: intercropping), passed to `compare.py --ignore`.
Remove an entry once the feature is ported.

To run the same comparison locally (Linux), from a C++ checkout at that commit:

```sh
python tests/run.py --monica <odin>/build/monica-run --engine odin --out results/odin
python tests/run.py --monica result/bin/monica-run --engine cpp --out results/cpp   # after nix build
python tests/compare.py results/cpp results/odin --ignore hohenfinow2/sim-min-ic
```

## Other pins worth knowing about

- **`flake.lock`** pins nixpkgs, which provides the Nix path's compilers,
  zeromq and `ols`. `nix flake update` moves all of them at once. Then run
  `check-pins` (the zeromq assertion) and `nix build`.
- **`pixi.lock`** pins conda-forge, which provides the pixi path's clang,
  libstdc++ headers and the glibc-2.28 sysroot. `pixi update` moves them.
- **`mas_cpp_misc`** (the submodule at the repo root) carries
  `cr_math/`, the CORE-MATH sources every transcendental call goes through
  (`CONVENTIONS.md` §1). It has no version of its own: moving the submodule
  moves it, for this port and the C++ alike. A new function goes in on the
  C++ side first (`mas_cpp_misc/cr_math/README.md`).
- **`DEBIAN_VERSION`** in the `Dockerfile` sets the image's zeromq, clang,
  libstdc++ and glibc. glibc includes libm, so this one affects the numerics:
  re-run `diff_vs_cpp.sh` after changing it.
- **monica-parameters:** the Docker image clones `MONICA_PARAMETERS_REF`
  (default `master`), as the C++ image does.
